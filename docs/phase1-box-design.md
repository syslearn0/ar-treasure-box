# Phase 1 — 箱の設計条件（ツール実測で判明した制約を反映）

`@8thwall/image-target-cli@1.0.0` のソースを読んで確認した、**実装上の強制条件**をまとめる。
ここは推測ではなく、CLI のコードから直接読み取った事実。

---

## 1. 決定的な制約：クロップ比が 3:4 か 4:3 に強制される

`src/interactive.js` の `selectPlanarGeometry()`:

```js
const height = Math.round((visualWidth * 4) / 3)   // 縦向きのとき
const width  = Math.round((height * 3) / 4)        // 横向きのとき
```

デフォルトクロップ（`crop.js: getDefaultCrop()`）も同じ比率に切り揃える。
**追跡対象領域は必ず 3:4（縦）か 4:3（横）になる。正方形にはできない。**

### 箱の設計への影響

| | 寸法 | ハガキ(100×148mm)への収まり | 箱としての自然さ |
|---|---|---|---|
| **4:3 横（推奨）** | **10cm × 7.5cm** | 余裕をもって収まる | 宝箱として自然 |
| 3:4 縦 | 9cm × 12cm | 縦にほぼ一杯 | 縦長すぎて箱に見えにくい |

→ **箱は 4:3 横、およそ 10cm × 7.5cm で設計する。**

重要なのは「クロップ枠を絵で埋めきる」こと。枠の中に白紙の余白が多いと、
その部分は特徴ゼロの死に領域になり、追跡の安定性を直接損なう。
箱の輪郭を枠いっぱいに広げるか、箱の周囲に不規則な影・木目・傷を描いて埋める。

## 2. 最小解像度

`constants.json`:

```json
{"minimumWidth": 480, "thumbnailHeight": 350, "luminanceHeight": 640, "minimumHeight": 640}
```

クロップ後が 480×640 px 未満だと `validateCrop()` が例外を投げて生成できない。

- 追跡に実際に使われるのは **高さ 640px にリサイズしたグレースケール画像**（`_luminance`）
- 10cm 幅の箱を 640px 相当で取り込むには **最低でも 200dpi**、
  余裕をみて **300〜600dpi でスキャン**するのが安全
- スキャナが使えない場合は、正面から真上・影なし・全体にピントが合った状態で撮影する

## 3. 生成物の置き場所は `image-targets/` で固定

生成される JSON:

```json
{
  "imagePath": "image-targets/box_luminance.png",
  "metadata": null,
  "name": "box",
  "type": "PLANAR",
  "properties": { "left":0, "top":0, "width":1200, "height":1600, "isRotated":false, ... },
  "resources": { "originalImage":"...", "croppedImage":"...", "thumbnailImage":"...", "luminanceImage":"..." }
}
```

`imagePath` は **ページからの相対URL**（CLI のソースにも `NOTE: This is a URL, not a relative path` とコメントがある）。
したがって出力フォルダ名は必ず `image-targets` でなければ、エンジンが luminance 画像を取りに行けない。
本プロジェクトでは `public/image-targets/` に置いてある。

## 4. ⚠️ CLI は特徴点の評価をしない

`metadata` が `null` のまま出力される。**特徴点の抽出はランタイム（エンジン内）で行われ、
CLI はグレースケール化とリサイズしかしない。**

つまり当初の計画にあった「`_luminance` 画像を見て特徴点の量と分布を確認する」は、
このCLI単体ではできない。Phase 1 の評価には別の手段が要る:

| 手段 | 入手性 | 出力 |
|---|---|---|
| `arcoreimg eval-img` | ARCore SDK に同梱。無料 | 0〜100 のスコア（75以上が目安） |
| OpenCV / 自作の FAST・ORB 検出 | 自前実装。無料 | 特徴点の位置を可視化 → **分布の偏りが見える** |
| 実機での体感テスト | 無料・最も確実 | 認識距離・角度・安定性 |

「量」は `arcoreimg` で数値化できるが、**「分布の偏り」はスコアに出ない**。
箱の左半分だけに特徴が集中していると、右半分が隠れたときに追跡が飛ぶ。
分布の確認には特徴点を可視化する経路が要る。

## 5. 箱の描画条件（要件6 ＋ 上記の制約）

- **4:3 横、10cm × 7.5cm。枠を絵で埋めきる**
- 黒ペンまたは濃いインク。**線を太く、濃く**（現行試作の「鉛筆線が薄い」を直す）
- 左右非対称にする
  - 左寄りに大きな錠前
  - 右上だけに金具
  - 右下に大きな木の節
  - 左上に斜めの傷
  - 大小の釘を不規則に
- 不規則な木目。**規則的な縞模様を作らない**（反復パターンはマッチングを壊す）
- 完全な左右対称を避ける
- 明暗の異なる領域を作る（面ごとにトーンを変える）
- 蓋と本体の間に濃い隙間を入れる
- **色よりグレースケール上のコントラストを優先**（追跡はグレースケールで行われる）
- 特徴が四隅まで散るように描く。中央だけ密で周辺が白、を避ける

## 6. 手順

```bash
# 1. 実物の箱をスキャン／正面撮影して work/box-scan.png に置く
#    （参考画像ではなく、必ずハガキに描いた完成版の実物）

# 2. ターゲット生成
npm run target work/box-scan.png box

# 3. public/image-targets/box.json ができる
#    src/config.ts の physicalWidthM / physicalHeightM を実測値に合わせる
```

生成をやり直す場合は同じコマンドで上書きされる（`OVERWRITE_FILES=true` を内部で設定済み）。
